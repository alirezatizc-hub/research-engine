# چرخهٔ بهینه‌سازی خودکار — `wallexbot/optimizer.py`

> هدف: موتور، خودش بک‌تست بگیرد، نتیجه را تحلیل کند، چند سناریو بسازد، روی پنجرهٔ اعتبارسنجی بسنجد و
> **یک** گزینهٔ برتر را برای تأیید انسان پیشنهاد دهد. هیچ پارامتری خودکار اعمال نمی‌شود.

```
داده ──► تقسیم سه‌پنجره‌ای (train / validation / test با شکاف purge)
         │
         ├─ دور ۱: ۸ سناریوی نام‌دار → بک‌تست روی train → رتبه‌بندی روی validation
         │        └─ تحلیل نتایج: AI (اختیاری) + جهش‌های محلی قطعی
         ├─ دور ۲: نامزدهای جدید → همان مسیر
         │
         └─ پایان: بهترین گزینه **یک‌بار** روی test سنجیده می‌شود
                    ↓
             proposal.json  (status = pending_approval)
                    ↓
             تأیید انسان → نوشتن در .env + باطل‌شدن WTB_LIVE_ACK
```

## ۱) تقسیم داده و ضدِ نشت

| پنجره | سهم | نقش |
|---|---|---|
| train | ۶۰٪ | انتخاب پارامتر (تنها پنجره‌ای که در جست‌وجو استفاده می‌شود) |
| validation | ۲۰٪ | رتبه‌بندی نامزدها |
| test | ۲۰٪ | فقط گزارش نهایی؛ **یک‌بار**، بعد از انتخاب |

- **شکاف purge**: بین پنجره‌ها ۸ کندل (۲ ساعت در تایم‌فریم ۱۵ دقیقه) حذف می‌شود تا اثر بسته‌شدن اجباری
  پوزیشن‌ها در مرز، به پنجرهٔ بعد نشت نکند.
- **زمینهٔ اندیکاتور**: هر پنجره از ابتدای تاریخچه تا انتهای خودش داده می‌بیند (`context`)، ولی
  `trade_from` مانع معامله قبل از شروع پنجره می‌شود. این کار هم ۱۲۰ کندل گرم‌شدن را هدر نمی‌دهد،
  هم نگاه به آینده را غیرممکن می‌کند (اندیکاتور فقط از گذشته ساخته می‌شود).
- **AI هم پنجرهٔ آزمون را نمی‌بیند**: در `_ai_summary` فقط `train` و `validation` فرستاده می‌شود؛
  یک تست واحد این را تضمین می‌کند (`test_cycle_produces_pending_proposal_and_hides_test_from_ai`).

حداقل داده: `180 + 2×40 + 2×8 = 276` کندل. برای نتیجهٔ معنادار، **۳۰ روز** داده لازم است
(`python -m wallexbot fetch --days 30`). دادهٔ ۱۹۲ کندلی فعلی عمداً رد می‌شود با پیام روشن،
چون تقسیم سه‌بخشی روی آن آماری بی‌معناست.

## ۲) امتیاز مرکب (چرا این فرمول)

```
score = بازدهی − ۲×حداکثر افت + ۱٫۵×(PF − ۱) + ۰٫۲×min(معاملات, ۱۰) − ۰٫۵×نوسان روزانه
```

- بازدهی تنها معیار نیست: افت، احتمال رد شدن در داوری (کنترل ریسک) را بالا می‌برد.
- `PF` فقط تا ۳ پاداش می‌گیرد تا یک معاملهٔ شانسی کل رتبه‌بندی را قبضه نکند.
- تعداد معامله تا ۱۰ پاداش دارد تا «معامله نکردن» برندهٔ الکی نشود.
- نوسان روزانهٔ بازده (`stability_pct`) جریمه می‌شود: دو مسیر با بازده یکسان، مسیر هموارتر بهتر است.

**ردی که باعث حذف سناریو می‌شود** (نه فقط امتیاز کم):

- `insufficient_trades(...)` — کمتر از `--min-trades` معامله در آن پنجره.
- `drawdown_over_limit(...)` — افت بیشتر از `WTB_MAX_DRAWDOWN` (پیش‌فرض ۵٪).

## ۳) سناریوها

۸ بستهٔ نام‌دار که نسبت به تنظیمات فعلی ساخته می‌شوند (نه اعداد ثابتِ کهنه):

| نام | ایده |
|---|---|
| `baseline` | تنظیمات فعلی (مرجع مقایسه) |
| `conservative` | فیلتر نوسان سخت‌تر، آستانهٔ بالاتر، معاملهٔ کمتر |
| `active` | آستانهٔ پایین‌تر، معاملهٔ بیشتر |
| `dip_only` / `breakout_only` | خاموش‌کردن یک الگو (`WTB_KINDS`) |
| `tight_stops` | استاپ/تارگت تنگ‌تر، خروج سریع‌تر |
| `wide_swing` | استاپ/تارگت گشادتر، نگه‌داری بلندتر |
| `fewer_bigger` | تمرکز روی بهترین سیگنال‌ها با حجم بزرگ‌تر |

دور دوم به بعد: **جهش محلی** (`mutate_scenarios`) — یک پارامتر، یک گام کوچک، حول بهترین گزینه
(`min_atr_pct ×{0.8,1.25}`, `rsi_buy ±3`, `bb_max_pos ±0.05`, `rules_min_score ±5`, `sl_atr ±0.3`, `tp_atr ±0.5`,
`max_trades_per_day ±5`).

## ۴) نقش AI (و مرزهایش)

پرامپت `SYS_OPTIMIZE` در `wallexbot/ai_agent.py`: تحلیل‌گر پژوهشی که تشخیص می‌دهد چرا سناریوها بعد از
کارمزد ضرر می‌دهند و حداکثر ۴ مجموعه‌پارامتر جدید پیشنهاد می‌دهد.

| قفل | جزئیات |
|---|---|
| فقط پارامترهای مجاز | جدول `allowed_space(cfg)` به AI داده می‌شود؛ کلید ناشناخته = رد |
| کران سخت عددی | `learner.bounds_for(cfg)` + کران‌های صریح (`ALLOWED`)؛ بیرون کران = رد |
| اعتبارسنجی نهایی | `Config.validate()` روی کاندید اجرا می‌شود (مثلاً `min_score ≤ rules_min_score`) |
| بدون دسترسی مستقیم | AI پارامتر را «اعمال» نمی‌کند؛ فقط سناریوی دور بعد را می‌سازد |
| شکست AI | خطا/JSON نامعتبر/بدون کلید ⇒ چرخه با جهش محلی ادامه می‌یابد (`ai.trace` ثبت می‌شود) |
| شفافیت | هر فراخوانی در `logs/ai_calls.jsonl` (مدل، تأخیر، هش پرامپت) و پاسخ در `report.json` |

## ۵) خروجی‌ها

```
logs/optimizer/<run-id>/
├── report.json      # همهٔ سناریوها، پنجره‌ها، trace AI، گاردریل‌ها، status
├── proposal.json    # پیشنهاد نهایی + diff نسبت به تنظیمات فعلی + recommend_apply
├── summary.md       # گزارش خوانا برای داوری/ویدیو
└── scenarios.csv    # جدول مقایسه (اکسل‌پسند)
```

نمونهٔ خروجی در [`docs/evidence/optimizer/`](evidence/optimizer/) نگه داشته شده است:
`report.json` + `proposal.json` + `scenarios.csv` از یک اجرای **مصنوعی** (فقط اثبات کارکرد لوله؛
برچسب `SYNTHETIC_NOT_EVIDENCE`) و `real_data_blocked.txt` که پیام مسدودشدن اجرای واقعی روی ۱۹۲ کندل را
نشان می‌دهد.

`proposal.json` تا زمانی که انسان تأیید نکند `status: pending_approval` است. اگر بازدهی پنجرهٔ
اعتبارسنجی مثبت نباشد، `recommend_apply: false` و هشدار ثبت می‌شود و اعمال، `--force` می‌خواهد.

## ۶) تأیید و اعمال

```bash
python -m wallexbot optimize --list                       # اجراهای قبلی
python -m wallexbot optimize --synthetic --rounds 2        # تست دود چرخه (بدون ادعای سود)
python -m wallexbot optimize --ai --rounds 2               # چرخهٔ واقعی روی data/ + AI
python -m wallexbot optimize --approve opt-20261023-1530 --yes   # اعمال پس از مرور
```

اعمال، این کارها را انجام می‌دهد:

1. فقط کلیدهای مجاز (`APPLY_KEYS`) را در `.env` می‌نویسد.
2. `WTB_LIVE_ACK` را حذف می‌کند (اثرانگشت پارامترها عوض شده؛ ACK قدیمی دیگر معتبر نیست).
3. یک رویداد `OPTIMIZE_APPLY` با شواهد (اعتبارسنجی/آزمون/مقادیر قبلی) در `logs/decisions.jsonl` ثبت می‌کند.
4. سپس باید `params` و `safetytests` دوباره اجرا شوند تا دروازهٔ live باز شود.

## ۷) پنل

تب **«بهینه‌سازی»**:

- انتخاب داده (واقعی/مصنوعی)، تعداد دور، حداقل معامله، فعال‌کردن AI.
- نوار پیشرفت زنده (`GET /api/optimizer` هر ۱٫۵ ثانیه).
- جدول سناریوها با بازده/افت/تعداد معامله در آموزش و اعتبارسنجی.
- کارت «پیشنهاد برای تأیید» + دکمهٔ **تأیید و اعمال در .env** (در `--demo`/`--read-only` غیرفعال).

| متد | مسیر | کار |
|---|---|---|
| GET | `/api/optimizer` | وضعیت اجرا + پیشنهاد + فهرست اجراها |
| GET | `/api/optimizer/<run-id>` | گزارش کامل یک اجرا |
| GET | `/api/optimizer/runs` | فهرست اجراها |
| POST | `/api/optimizer/start` | `{synthetic, ai, rounds, min_trades, purge}` |
| POST | `/api/optimizer/stop` | توقف تمیز بین سناریوها |
| POST | `/api/optimizer/approve` | `{run_id, confirm:true, force?}` |

## ۸) تست‌ها

`tests/test_optimizer.py` (۱۷ تست):

- سه پنجرهٔ پیوسته و بدون هم‌پوشانی؛ شکاف purge؛ `context` فقط گذشته.
- رد دادهٔ کوتاه با پیام راهنما.
- امتیاز: حذف کم‌معامله و افت بیش از سقف؛ رتبهٔ بهتر برای ریسک‌تنظیم‌شده‌تر.
- کران‌ها: کلید ناشناخته/بیرون‌کران رد؛ `min_score ≤ rules_min_score` تضمین.
- چرخه: پیشنهاد `pending_approval`، عدم استفاده از test در انتخاب (شمارش فراخوانی‌ها)،
  نشت‌نکردن test به AI، ادامهٔ چرخه وقتی AI خطا می‌دهد.
- اعمال: نیاز به تأیید، نوشتن `.env`، حذف ACK، ثبت لاگ، جلوگیری از اعمال دوباره، نیاز به `--force`
  وقتی اعتبارسنجی منفی است.

## ۹) محدودیت‌ها (صادقانه)

- روی ۲ روز داده هیچ ادعای بهینه‌سازی نمی‌شود؛ چرخه عمداً خطا می‌دهد و `fetch --days 30` می‌خواهد.
- دادهٔ مصنوعی فقط برای اثبات کارکرد لولهٔ چرخه است (`SYNTHETIC_NOT_EVIDENCE`).
- بهینه‌سازی، سود را تضمین نمی‌کند؛ هدفش «کاهش ضرر و افزایش پایداری با شواهد» است.
- تعداد معاملات در ۳۰ روز هم کم است؛ به همین دلیل حداقل معامله و پایداری روزانه در معیار آمده‌اند
  تا یک برد شانسی برنده نشود.
